# TV Box repo knowledge

TV Box is "Letterboxd, but for TV shows": a small-group app for tracking, rating, and discussing TV shows episode by episode. It's a static single-page app (GitHub Pages) with no backend server of its own -- everything talks directly to Supabase and TMDB from the browser.

Read this before making changes so you don't re-derive things that are already established, and so new code lands in the pattern the rest of the repo already follows. If something here looks stale (a file moved, a convention changed), trust the actual repo state over this document and consider updating this file.

## Stack

React 19 + TypeScript, Vite, Tailwind CSS 4, react-router v6 (`HashRouter`, since GitHub Pages has no server-side routing), framer-motion, Supabase (Postgres 17 + `@supabase/supabase-js`, permissive RLS on most tables, passkey/WebAuthn sign-in via Edge Functions -- see `supabase/functions/webauthn-registration-options/README.md`), TMDB API for show/episode data, TVmaze as a secondary source for air-date corrections. Vitest + React Testing Library + jsdom for tests, oxlint for linting.

## Directory map

- `src/pages/` -- one component per route. See `src/lib/routes.ts` for the `ROUTES` map and route-builder helpers (`showRoute`, `profileRoute`, etc.) -- always build hrefs through these, never hand-write a path string.
- `src/components/` -- shared UI. `src/components/showDetail/` holds the subcomponents composing the show detail page specifically (`ShowDetailHero`, `ShowDetailQuickActions`, `ShowDetailProgress`, `ShowDetailStreaming`, `ShowDetailSeasons`). `src/components/profileActivity/` holds the Profile page's tab contents (`DiaryTab`, `WatchlistTab`, `DroppedTab`, `ListsTab`).
- `src/lib/` -- data access (Supabase queries, TMDB/TVmaze clients) and pure business logic (activity/diary building, date handling, streaming-provider resolution). No React here -- this is what makes `showActivity.ts`, `pagination.ts`, `date.ts`, `seasonProgress.ts` etc. straightforward to unit test.
- `src/hooks/` -- reusable hooks (`useToast`, `useScrollRestoration`, `useEscapeAndFocusReturn`, `useOutsideClick`, `useStreamingPlatforms`) and page-level state hooks that own a single page's data loading and mutations. `useShowDetail` (backing `ShowDetail.tsx`) is the biggest: it's a thin orchestrator over `src/hooks/showDetail/*` -- one hook per concern (streaming provider, air dates, watchlist, now-watching/dropped, episode-watch handlers, ratings, rewatches) -- rather than one large hook owning everything itself.
- `src/contexts/` -- `AuthContext` (the logged-in `AppUser`, backed by localStorage, no real session/token) and `ThemeContext` (light/dark theme, plus a separate glass-transparency override -- see App chrome below -- both follow the OS by default), provided at the app root.
- `src/test/` -- test-only infrastructure: `setup.ts` (registers RTL's `cleanup()`), `supabaseMock.ts` (chainable Supabase query-builder mock), `framerMotionMock.tsx` (synchronous framer-motion test double -- see Testing below for *why* this exists).
- `supabase/schema.sql` -- full schema + RLS policies. Idempotent and safe to re-run (`create table if not exists`, `drop policy if exists` before every `create policy`). This is the source of truth for the data model -- read it directly rather than trusting a summary, including this one.
- `supabase/functions/` -- Edge Functions (passkey sign-in, Web Push, bug reports, the Shortcuts API). Each folder has its own README with deploy instructions; see `DEVELOPMENT.md`'s Edge Functions section for which are required vs. optional.
- `scripts/backfill-runtime.mjs` -- one-off maintenance script, not run by CI or the app.

## Data model, at a glance

Core tables: `users`, `episode_watched` (the per-episode watch log; `show_total_episodes` is a denormalized snapshot used to compute "finished"), `show_ratings`, `season_ratings`, `show_started`, `show_watching_dismissed`, `show_dropped`, `show_rewatches`, `watchlist`, `show_lists` + `show_list_items`, `show_streaming_overrides`, `follows`, `notifications`, `webauthn_credentials` + `webauthn_challenges` (passkeys; RLS enabled with no policies -- service-role only), `push_subscriptions` (Web Push), `personal_access_tokens` (Shortcuts API). Two Postgres views, `episode_watched_show_summary` and `episode_watched_undated_summary`, pre-aggregate per-show watch totals so Profile stats don't have to paginate and sum raw rows client-side (see the Performance section below).

A show's state is a composition of independent, orthogonal flags, not a single enum: it can be started, have N episodes watched, be on the watchlist, be dismissed from Now Watching, and be dropped, all at once or in various combinations. `src/lib/showActivity.ts`'s `summarizeShowActivity` is where these get merged into one `ShowActivity` row per show, and `nowWatching` / `watchHistory` are the filters that turn that into "what shows on Home" vs. "what shows in History". If you're adding a new per-show status, this is the file to extend, and it already has a `.test.ts` covering all the derived-state edge cases -- use it as a reference for what "finished" logic and Now Watching eligibility currently mean before changing them.

## Established conventions

**Comments.** Only functions/methods -- and meaningfully-named exported constants where the name alone doesn't convey the "what" (e.g. `GLASS_SPRING` in `motion.ts`, `estimatedShowRating` in `useShowRatingsState.ts`, `VAPID_PUBLIC_KEY` in `constants.ts`, `PILL_SIZE_CLASSES` in `Chip.tsx`) -- get a doc comment, and it's exactly one line. No paragraph comments, no inline reasoning comments, no comments on type/interface fields, no section-divider comments. `eslint-disable-next-line` directives are the one exception (they're compiler directives, not documentation, and are preserved). This was a deliberate, repo-wide decision, not an oversight -- don't reintroduce explanatory paragraph comments even for a genuinely tricky piece of logic; if it needs explaining, either the one-line doc captures the "what," or the code itself should be made clearer.

**Encapsulation / no unnecessary private methods.** This codebase is almost entirely functional (hooks + components, not classes), so there's rarely a literal "private method" to avoid. The rule shows up instead as: extract multi-step logic to a named, top-level, independently-testable function (in `src/lib/` or a dedicated hook) rather than burying it in a closure nested inside a component or another function, unless it's genuinely only ever one call site long and trivial. `src/hooks/showDetail/` (one hook per concern) is the precedent for "split by responsibility" over "one large function/class owning everything." In the rare case a class is warranted (currently just `ErrorBoundary`, which needs `componentDidCatch`), avoid adding private instance methods unless the logic truly needs instance state.

**Never `window.confirm()`.** Destructive/bulk actions use an inline expand-to-confirm pattern instead (see `DateMarkControl.tsx`, `InlineConfirmCancel.tsx`) -- the confirm step is a second click revealed inline, not a native dialog.

**Motion, UX, and UI polish.** All framer-motion variants/durations/easings live in `src/lib/motion.ts` as named exports (e.g. `TRIGGER_SWAP_MOTION`, `DROPDOWN_PANEL_INITIAL/ANIMATE/EXIT`, `staggerRowMotion`) -- new animated UI should reuse or extend these rather than inlining ad hoc `transition={{...}}` objects, so timing stays consistent across the app. `scrollBehavior()` and `prefersReducedMotion()` gate direct `window.scrollTo` calls; `MotionConfig reducedMotion="user"` at the app root handles framer-motion's own animations. Beyond timing, the repo has been explicitly audited more than once for "does this feel buttery smooth and modern": no abrupt state swaps (`InlinePanel` handles trigger-vs-open-panel swaps), skeleton loaders (`Skeletons.tsx`) instead of layout jump on any network-backed view, and visual consistency (spacing/radius/color) with the rest of the page a new UI element lives on -- this is a "does it match the rest of the app" judgment call as much as a fixed rule. Haptic feedback on a tap uses the shared `HapticOverlay` component (a full-coverage, invisible `<input type="checkbox" switch>` rendered inside the actual tap target, with `touch-manipulation` so Safari's native switch drag-to-toggle gesture doesn't swallow a scroll swipe when the tap target sits inside a horizontally-scrolling row like `ProfileActivity`'s tab strip) -- don't hand-roll a haptic trigger, and especially don't reach for a hidden singleton toggled via a programmatic `.click()`, which looks plausible but Safari silently won't fire the haptic for (it only fires for a tap that physically lands on the switch element itself).

**App chrome.** `Navbar.tsx` is deliberately minimal, matching the reference iOS/Apple TV app: a `glass-surface` top bar, pinned with `position: sticky` at every breakpoint (not just desktop -- a mobile-only transparent header used to let scrolling content show through/collide with the bar, which read as the bar itself moving), holding the "TV Box" logo+wordmark on the left and report-a-bug/theme/notifications icons on the right, and on mobile a floating `glass-surface-strong` pill bottom tab bar inset from the screen edges rather than a full-width bar, with a `layoutId`-based sliding pill (`mobile-tab-pill`) behind the active tab rather than a small dot. Theme has two entry points -- the top-bar quick toggle and the fuller control in Profile > Appearance -- both reading/writing the same `ThemeContext`, so keep them in sync rather than duplicating state. Report a bug (`ReportBugPanel.tsx`) lives only in the top bar now, not in Profile's More menu -- it moved back and forth once already, so check CHANGELOG.md before assuming either placement if this surfaces again. Glass-transparency stays Profile-only. Each page supplies its own large title via the shared `.large-title` class instead of Navbar owning a page title; it collapses via a pure-CSS scroll-timeline animation in `index.css` (no scroll listener, no layout thrash) that fades and slides the title away as the page scrolls, falling back to a static title via `@supports` on browsers without scroll-driven animations, and skipping the animation entirely under `prefers-reduced-motion`. `ThemeContext`'s `Transparency` setting (`'system' | 'reduced' | 'full'`, persisted via `STORAGE_KEYS.transparency`) overrides the OS's Reduce Transparency preference in either direction and is boot-applied in `index.html` before first paint the same way theme is, to avoid a flash. `body` uses `overflow-x: clip`, not `overflow-x: hidden` -- per the CSS Overflow spec, pairing `overflow-x: hidden` with the default `overflow-y: visible` computes `overflow-y` as `auto`, silently turning `body` into a scroll container and breaking any `position: sticky` descendant (this is what broke the notifications bell in an earlier pass); `clip` doesn't trigger that fixup.

**App icon / AppLogo.** The favicon, apple-touch-icons, and PWA manifest icons are rasterized from the two source SVGs in `design/` (`app-icon-dark.svg`/`app-icon-light.svg`, one per theme) by `design/generate-icons.js` (`npm run icons`, uses `sharp`) -- regenerate every PNG in `public/` from those sources after editing either SVG rather than hand-editing a PNG (sizes are apple-touch-icon-{120,152,167,180}, icon-{192,512}, each with a `-light` sibling for the light-theme variant). The icon deliberately uses its own neutral slate-glass tokens (`--color-icon-bg-1`/`--color-icon-bg-2` in `index.css`) rather than the violet `--color-accent-*` tokens, so the mark reads as glass rather than a brand-color badge -- `AppLogo.tsx` (the same mark inlined in the navbar/Login/PasscodeGate) reads from the same tokens, so a palette change only has to happen once.

**Shared pill styling.** Every pill-shaped filter/select control -- `Chip`, `SegmentedControl` options, Profile's Diary/History/Watchlist/Dropped/Lists tab switcher, and the "Filter by person"/"Filter by genre"/"Filters" trigger buttons on Activity, Search, and History -- shares its sizing and color classes (`PILL_SIZE_CLASSES`/`PILL_ACTIVE_CLASSES`/`PILL_INACTIVE_CLASSES`, exported from `Chip.tsx`) instead of each call site hand-writing the same literal class string. Import and reuse these for any new pill-shaped control rather than copying the classes, so the whole set stays in sync if the sizing or colors change later.

**Floating dropdown vs. page-pushing panel.** Choose by what the control IS, not by which pattern happens to be more common in the file: a short picklist/menu where you pick one item (e.g. `PersonFilterPanel`) is a floating/absolute dropdown (`DROPDOWN_PANEL_*` motion tokens, `absolute right-0 top-full z-50`, its own outside-click listener) that overlays content without moving it; a content-filter form attached to what's below it (e.g. `HistoryFiltersPanel`, `SearchFiltersPanel`) is an `InlinePanel` that pushes the page down. Getting this backwards reads as broken UX even when the code works fine -- this was hard-won user feedback and shouldn't be re-litigated per component. Any panel with a capped scroll height (`max-h-* overflow-y-auto`) should also get the `scroll-fade-bottom` utility class (`index.css`) -- a `mask-image` edge fade that hints there's more content to scroll to without needing JS overflow-detection. `DropdownPanel`'s `right-0` anchors to its own trigger's wrapper, not the row -- if that trigger shares a `flex-wrap` row with something that can push it onto its own line (e.g. Activity's person-filter next to its scope `SegmentedControl`), give the trigger's wrapper `ml-auto` so it stays pinned to the row's right edge whether or not the row has wrapped; without it, a wrapped trigger sits flush left and the dropdown opens off the left edge of the screen.

**Production-only CSS gotcha.** `backdrop-filter` must be declared *after* its `-webkit-backdrop-filter` prefix in `index.css`'s `.glass-surface*` classes, not before -- Lightning CSS's minifier (used by the production build only, not `npm run dev`) silently strips the standard property when it comes first, leaving every glass panel flat/unblurred in the deployed app while looking correct locally. If you touch these classes, verify the fix survives minification by inspecting the built CSS in `dist/assets/*.css` directly, not just `npm run dev`.

**Error handling.** Optimistic UI updates roll back on failure and surface an error via the shared `useToast` hook (`showError`/`showUndo`), not a silent catch. Bulk mutations that can overwrite existing data offer an "Undo" toast action backed by a pre-mutation snapshot (see `handleMarkAllWatched`/`undoBulkMark` in `src/hooks/showDetail/useEpisodeWatchHandlers.ts`) rather than requiring a confirmation dialog up front. Every `ToastState` carries a unique incrementing `id`, used as `Toast.tsx`'s React `key` instead of the message text -- two toasts with identical text shown back-to-back need to actually remount (and restart their auto-dismiss timer), which keying on `message` silently breaks.

**Accessibility.** Toggle-style buttons report state via `aria-pressed`, not just a visual class swap. Panels/modals use `useEscapeAndFocusReturn` for Escape-to-close and returning focus to the trigger element. Touch targets follow a ~44px minimum.

**Unreleased content can't be acted on yet.** An episode (`EpisodeRow`) or a season (`ShowDetailSeasons`) with an `air_date` still in the future (`isFutureDate` in `lib/date.ts`) gets an "Airs <date>" badge instead of its normal watch/rate control -- a new affordance on show/season/episode data should follow the same rule rather than letting people mark-watched or rate something that hasn't aired. `TmdbSeasonDetail.air_date` mirrors what TMDB's season endpoint already returns; a null/missing date is treated as "not upcoming" (allowed), matching how episodes already handle an unknown air date.

**No fabricated data.** Don't invent plausible-looking placeholder values for a real user's row to "fix" a display bug -- use the app's actual "unknown" state (e.g. `watched_at_unknown`, `UNKNOWN_WATCHED_AT`) instead of guessing a date.

**No local staging database.** There's one Supabase project. Any DB-level testing or live-browser QA against real data must clean up the fake rows/follows/notifications it creates -- shared feeds (Activity, notifications) are visible to the whole group, so test pollution is a real user-facing bug, not just noise.

**Commit discipline.** Always `git commit` locally; never `git push`. The user pushes when ready. Prefer several small, logically-scoped commits over one large one for a multi-part change.

## Performance patterns already in place

- `src/lib/pagination.ts`'s `fetchPaginated` works around PostgREST's 1000-row-per-request cap by paging with parallel `.range()` requests -- use it (or `supabase.range()` directly with awareness of the cap) rather than assuming a single `.select()` returns everything for a user with a large history.
- Profile stats are served from the two aggregation views mentioned above instead of summing raw `episode_watched` rows client-side -- this took a ~1.2s load down to ~90ms. If you're adding a new stat, check whether it can be added to one of those views before reaching for a client-side reduce over paginated raw rows.
- TMDB/TVmaze lookups are session-cached at module scope (`showDetailCache`/`watchProvidersCache` in `tmdb.ts`, `seasonCache`/`nextEpisodeCache` in `seasonProgress.ts`, `showIdByImdbId`/`airDatesByTvmazeShowId` in `tvmaze.ts`) -- these caches are why `fetchSeasonBreakdowns`/`fetchNextEpisode` tests use distinct show IDs per test case, to avoid one test's cached result leaking into another's assertions.
- `streamingProvider.ts`'s per-show/region cache holds both a show's full resolution: `resolveShowPlatforms` returns each show's single "best guess" pick (for a one-line "where to watch" badge, e.g. `ShowCard`'s `provider` prop) and `resolveShowPlatformNames` returns the *full* deduped set of every non-low-signal service it streams on, sharing the same cache/fetch so calling both for the same shows/region never double-fetches. Use `resolveShowPlatformNames` (surfaced as `useStreamingPlatforms`'s `platformNames`) for anything that filters/facets "is this show on platform X" -- reusing the single-pick badge data for a filter silently hides shows where some other service outranks the one being filtered for.
- Polling on an interval (`NotificationsBell`'s unseen-count refresh) skips the request while `document.hidden` and catches up immediately via a `visibilitychange` listener instead -- new polling should follow this pattern rather than fetching on a fixed timer regardless of whether the tab is backgrounded.
- A mutation-handler callback passed as a prop to a `React.memo`-wrapped row component (e.g. `EpisodeRow`) must keep a stable identity across the state updates it itself causes, or the memoization is silently defeated and every row re-renders on every toggle. The fix isn't to drop the handler's own state from its closure -- it's `useCallback` with the state read through a ref kept current via `useLayoutEffect` (never assigned directly during render -- oxlint's `react(refs)` rule catches that) instead of the state value itself in the dependency array; see `useEpisodeWatchHandlers.ts`'s `handleToggleWatched`/`watchedRef` for the reference implementation. Derived values passed down the same tree (a `.map()`-computed episode list, a per-item corrected date) need the matching `useMemo`/`useCallback` treatment or they reintroduce the same fan-out from the other side.
- A `pointerdown`-outside-closes-panel effect (dropdowns, filter menus) is the shared `useOutsideClick` hook, not a hand-rolled `useRef`+`useEffect` pair -- it was previously copy-pasted across `Navbar`, `Search`, `Activity`, and `Profile` before being deduped. Day-bucketing a list of timestamped entries into "grouped by day" sections is `groupByDay` in `lib/date.ts`, likewise deduped from `Activity.tsx`/`ProfileActivity.tsx`.

## Testing

Vitest + React Testing Library + jsdom, configured in `vite.config.ts`'s `test` block. Run with `npm test` (single run), `npm run test:watch`, or `npm run test:coverage`. `src/test/setup.ts` wires up jest-dom matchers and RTL's `cleanup()`.

**Coverage bar: >80% on every metric** (statements, branch, functions, lines), with meaningful positive *and* negative flows covered, not just happy paths -- this is a hard repo-wide target, not a nice-to-have. As of the last full pass the repo sits at roughly 94% statements / 88% branch / 92% functions / 97% lines across 139 test files (1299 tests) -- there are no remaining zero-coverage files. When adding coverage, run `npx vitest run --coverage --coverage.reportsDirectory=/tmp/tv-box-coverage` rather than the bare `--coverage` flag -- see the next section for why. If a fix surfaces a real bug while writing its test (not just a missing test), fix the bug as part of the same pass rather than only adding a regression test around the buggy behavior.

Two gotchas worth knowing before writing a new test:

1. **framer-motion's `AnimatePresence mode="wait"`** never resolves its exit transition under jsdom, so a component that swaps between two `motion.*` children via `AnimatePresence` (like `DateMarkControl`'s trigger-vs-form swap) will appear stuck on the old child forever in a naive test. Mock `framer-motion` with `src/test/framerMotionMock.tsx` (`vi.mock('framer-motion', () => framerMotionMock)`) in any test that renders a component using `AnimatePresence` for conditional swapping. That mock's `motion.*` proxy caches each tag's component by name deliberately -- an uncached version returns a new component identity on every property access, which makes React treat every re-render as a full remount and silently detaches DOM nodes you queried earlier in the test. Testing `App.tsx` itself needs a local extension of this mock adding a `MotionConfig` passthrough, since the shared mock doesn't export it.
2. **Supabase's chained query builder** (`.from().select().eq().order()...`) is mocked via `src/test/supabaseMock.ts`'s `createQueryBuilder`, which returns an object where every chain method returns itself and the object itself is thenable -- so it resolves correctly regardless of which method happens to be last in a given call (`.range()`, `.single()`, `.maybeSingle()`, or none of those). Mock `../lib/supabase` at the top of the test file and set `vi.mocked(supabase.from).mockReturnValue(builder)` per test.

Other gotchas hit while building out coverage: jsdom doesn't implement `scrollIntoView`, `setPointerCapture`, or `window.scrollTo` -- stub each with `vi.fn()` in `beforeEach` wherever the component under test calls them. `PosterTile`/provider-logo components render the show/provider name as plain fallback text when there's no image, which collides with an adjacent caption `<p>` showing the same name -- give list-item test fixtures a non-null poster/logo path to avoid "found multiple elements with text" failures. `React.lazy`'s dynamic `import()` still resolves through `vi.mock`, but always via a microtask even when mocked -- use `await screen.findByText(...)` rather than `getByText` for anything behind a lazy boundary (see `App.tsx`'s route tests).

CI (`.github/workflows/deploy.yml`) runs lint, then test, then build, before the GitHub Pages deploy job -- a failing test or lint error blocks deploy.

## Where things are documented

`README.md` is the user-facing feature list (what the app does, from the user's point of view -- keep it in sync when you ship a user-visible feature). `DEVELOPMENT.md` is the contributor setup/scripts/structure reference. `CHANGELOG.md` follows Keep a Changelog format, with an `[Unreleased]` section for shipped-but-not-tagged work.
